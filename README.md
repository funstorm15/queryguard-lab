# QueryGuard Lab

A small lab for seeing what goes wrong when an app trusts SQL generated by an LLM — and testing the code that should stop it.

Imagine a sales chatbot that can answer “show my orders.” What happens when someone asks it to ignore the rules and show another customer's orders? QueryGuard runs that request against two versions of the same app, then shows the SQL, returned rows, and any data the user shouldn't have received.

The browser UI, terminal commands, and tests all use the same Python code. Everything runs against fake data in SQLite. Each request starts with a fresh database.

## Try it

You need **Python 3.11+** with `sqlite3`. No API key or third-party runtime packages are needed for the demo.

From the project folder:

```bash
python3 -m queryguard ui
```

The browser opens at **http://127.0.0.1:8765**. Keep the terminal running while you use it. On Windows, use `python` if that's your Python command.

1. Leave the provider set to **Демо-симулятор**.
2. Choose **Мои заказы** and click **Запустить запрос** to try a normal request.
3. Choose **Обход прав пользователя**, select **Сравнить**, and run it again.
4. Look at the two results. The vulnerable version returns another tenant's orders; the protected version rejects the attempt.
5. Open **Проверки** to run all nine cases and inspect their results.

The UI labels are mostly Russian. The demo prompts are English because the simulator recognizes a small set of phrases. SQL and diagnostic output are shown as returned. Use **↓ JSON** to save a result before reloading the page.

**The default demo is scripted.** It deliberately produces bad completions so you can see their consequences. It does not prove that a real model will fall for the same prompt. An optional Ollama adapter lets you run the cases with an actual local model.

## Why this project exists

A query can be valid SQL and still read data the user has no right to see. Telling a model “only show this user's records” leaves that decision with the model. This lab makes the failure visible and puts the permission check in application code.

It is useful for learning the difference between prompt injection, SQL injection, and missing authorization. It also gives you repeatable tests to run when changing the query-handling code. The current version tests its own small app; it doesn't scan arbitrary websites or automatically solve CTF challenges.

## Two ways to handle a question

| | Vulnerable | Protected |
| --- | --- | --- |
| Model output | A SQL statement | A small JSON plan |
| Who chooses the tenant? | The generated query | Application code |
| Customer input | The demo includes an unsafe SQL completion | Passed as a bound value |
| Private fields and writes | Available in the fake database | Excluded by the compiler and database guard |

For example, the protected version accepts:

```json
{"action": "list_orders", "customer": "O'Brien", "limit": 20}
```

It checks the fields, supplies the tenant, and builds SQL from a fixed template. The model cannot choose a table, add a SQL expression, or override the tenant. A separate SQLite authorizer restricts fields, functions, and writes. **Tenant filtering belongs to the query compiler**; the authorizer does not enforce row-level access.

Both versions restrict SQL to the disposable fixture. Neither accepts a real database connection. The UI's tenant selector simulates a logged-in user; it isn't an authentication system.

## What's covered

The suite includes three ordinary requests — order listing, a sales total, and a customer name containing an apostrophe — plus six attack cases:

- Asking for every tenant's orders.
- Requesting a private column.
- Reading the synthetic secrets table.
- Trying to delete orders.
- Putting SQL syntax into a customer name.
- Hiding instructions in retrieved document text.

The scripted run produces these results:

| Mode | Observed violations | Rejected plans | Expected results |
| --- | ---: | ---: | ---: |
| Vulnerable | 6 | 0 | 3 |
| Protected | 0 | 5 | 4 |

A finding needs observable evidence: returned fixture values that should be private, or a change to database contents. Model and SQL errors are reported separately. “Not observed” means the test didn't find a violation, not that the app is secure. These checks can miss transformed, aggregate, or timing-based leaks; see the [threat model](docs/THREAT_MODEL.md).

## Terminal version

```bash
python3 -m queryguard scan
python3 -m queryguard ask "Show my orders"
python3 -m queryguard ask "Show orders for all tenants" --mode vulnerable
```

A scan writes `reports/report.html` and `reports/report.json`. The HTML report can be opened directly in a browser. Example output is included as [HTML](examples/simulated-report.html) and [JSON](examples/simulated-report.json); download the HTML to view it rather than its source on GitHub.

The default scan exits successfully when the protected cases have no violations or test failures. The deliberately vulnerable examples still appear as findings. Use `--fail-on any` if those should also cause a nonzero exit. Full options and outcome definitions are in the [CLI reference](docs/CLI.md).

## Use an installed Ollama model

Start [Ollama](https://ollama.com/) and get an installed model's exact name with `ollama list`. Then select Ollama in the UI, or run:

```bash
python3 -m queryguard scan --provider ollama --model YOUR_INSTALLED_MODEL
```

The adapter calls the local [`/api/chat` endpoint](https://docs.ollama.com/api/chat). It doesn't download models. The UI uses `127.0.0.1:11434` and waits up to 60 seconds per call; the CLI also accepts `--ollama-url` for another loopback origin and `--timeout` up to 300 seconds. A full comparison makes 18 sequential calls.

Live Ollama testing is still pending. The adapter has mocked request/response tests; the included results are from the simulator. The two modes also ask for different output formats, so this is a comparison of application designs, not a benchmark of one model prompt.

## Development

```bash
python3 -m unittest discover -s tests -v
```

The suite covers authorization, parameter binding, database changes, malformed output, provider failures, reports, and the local HTTP interface. For the checks actually performed, see [validation notes](docs/VALIDATION.md).

You can run from source without installing anything. For the `queryguard` command, create a virtual environment and run `python -m pip install .`. Setuptools is a build dependency. GitHub Actions tests Python 3.11–3.14 and uploads scan reports.

The main files are:

- `policy.py`: validates plans and builds protected queries.
- `database.py`: creates the fake database and installs SQLite restrictions.
- `engine.py`: runs a request and records what happened.
- `cases.py` and `scanner.py`: define scenarios and check their results.
- `providers.py`: contains the simulator and Ollama adapter.
- `ui.py` and `static/`: serve the local browser interface.

For another UI port, run `python3 -m queryguard ui --port 8888`. Add `--no-browser` to skip opening a tab automatically. The server binds to loopback only; it isn't intended for public hosting. Results stay in tab memory. UI JSON exports use `ui_session_version: 1`, a separate format from CLI reports, and incomplete suites are marked `complete: false`.

More detail: [architecture](docs/ARCHITECTURE.md), [walkthrough](docs/DEMO.md), [contributing](CONTRIBUTING.md), and [security scope](SECURITY.md).
